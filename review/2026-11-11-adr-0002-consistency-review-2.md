## Verdict

The third review's fixes left nothing behind: no "Option A1", no "eleven", no old value numbers, no range of names, and every anchor, number, name and reference holds. What is left is one place where the record contradicts its own catalogue (a required field that one reply never carries), one overclaim in the Appendix intro, one announced-but-unused kind of gap, and a question for the user about citing the hurl suite's internal status file. The rest is small: a measurement that describes half of a reply, a success criterion that assumes an NFS baseline that does not exist, and a few references that are loose. None needs new evidence; three need the user.

## Medium

1. **Table 2 makes snapshot `name` a required read field, and the reply by name has none.** The row for "a required read field absent from a reply" (L609) lists "volume and snapshot `name`" in its first list. [bug_plugin_rest_zvol_snapshot_name_missing](../docs/adr/0002-api-v4-support-jdss1.md#bug_plugin_rest_zvol_snapshot_name_missing) (L2168–2174) says a zvol snapshot GET has no `name` key, and the observed types agree: `empirical/jdss1/v4/typespec/pools/+poolname+/volumes/+volumename+/snapshots/+snapshotname+/GET.tsp` has `creation`, `volsize` and an optional `clones`, no `name`; the all-snapshots list (`volumes/snapshots/GET.tsp:45`) has it. As written, the rule would fail every zvol GetVolumeSnapshot with "name missing". The mapping is per endpoint (Terms, L2598), so the fix is a qualification: "snapshot `name` in list entries; the reply by name carries none and nothing reads it there". No decision needed, but the sentence is a rule the generator will implement, so it should be exact.
2. **The Appendix intro overclaims.** "Every finding this document refers to, each described once; the rest of the text uses only the name, as a link" (L1670–1671). Thirteen names the record refers to have no entry and appear in code font, as the README's rule says they should (L128–130): `bug_plugin_driver_nas_quota_null_size_zero`, `bug_plugin_node_iscsi_login_failure_ignored`, `bug_plugin_node_unstage_no_logout`, `bug_plugin_rest_delete_share_nil_descriptor`, `bug_plugin_rest_nas_snapshot_create_copy_of_volume_create`, `crash_plugin_ctrl_create_snapshot_empty_name`, `crash_plugin_ctrl_create_volume_on_rest_error`, `crash_plugin_ctrl_get_capacity_no_logger`, `crash_plugin_driver_id_index_without_length_check`, `crash_plugin_driver_snapshot_name_empty`, `crash_plugin_driver_volume_desc_empty_value`, `security_plugin_rest_request_dump_every_call`, `security_plugin_secrets_in_logs`. The intro should say what is true: every finding this document fixes or rests on has an entry here; a name in code font is one described in the reviews or the tracker, found through [ID sources](../docs/adr/0002-api-v4-support-jdss1.md#id-sources).
3. **The third kind of gap is announced and never used.** The Evidence gaps intro (L1716–1717) names three kinds: a request sent differently, a situation never recorded, and "code with no evidence behind it", and says each gap states its kind. The twelve `Kind` rows hold only the first two: four and eight. The three `gap_plugin_rest_*` entries, `gap_plugin_rest_appliance_unreachable` (L1807), `gap_plugin_rest_unexpected_reply_bodies` (L1815) and `gap_plugin_rest_failover_during_call` (L1824), are the third kind by their area and by their "Plugin code that depends on it" rows (`Send`, `getError`), but their rows say "a situation that was never recorded". Either their `Kind` rows change to the third kind, or the intro names two kinds. The third review removed the orphaned sentence that once introduced the third kind (its item 12); this is the other half of that leftover.
4. **For the user: the hurl suite's `project-status.md` is cited as a source.** Table 4 (L1683) and Table 5 (L1887) name `empirical/hurl/project-status.md` as where the numbered findings live, and the Relationship section (L1507) names `kub-testing/project-status.md` beside `ISSUES.md`. On 2026-11-08 the user said the hurl file is an internal document, kept by the agent for the agent, not for public view, and that public documents should describe results through the generated specs and `bug-reports/`, not through Finding numbers; kub-testing's file carries the same "Maintained by the agent" header. The ADR convention says the opposite for records: "the spec repository's findings by their number, since that repository is read only for this work" (README L172–173), and the record cites hurl Findings 4, 4.4, 7, 8, 9, 14, 15, 20, 21 and 22 in 26 places. Whether a record in the plugin repository counts as a public document is the user's call. If it does, the two table rows should point at `bug-reports/` and the generated specs, and the Finding citations need a home that readers can open.

## Low

5. **The observed types of the volume reply describe only the zvol alternative.** Measurements (L2539–2541): "volume by name: … `origin`, `clones`, `quota` `null` in every recording; `is_clone` `false`". The record itself says a zvol and its clone are separate alternatives split on `is_clone` (L253; Table 2, L614), and the TypeSpec of the reply by name has both: `is_clone: false` with `origin: null` (lines 229, 247) and `is_clone: true` with `origin: string` (lines 350, 368). Say "in the zvol alternative; in the clone alternative `is_clone` is `true` and `origin` a string, `clones` and `quota` `null` in both".
6. **The success criterion assumes an NFS baseline.** "its results on v4 would be the same as, or better than, before the move, for both drivers" (L155–157), while step 5 says "There is no NFS baseline: no NFS build has ever been run live" (L1380–1381) and gives the NFS cycle its own pass conditions. Say "for iSCSI; the NFS cycle has no baseline and passes on step 5's conditions".
7. **"risks 4 to 13" as the risks of stages 3 and 4** (Consequences, L1027): risk 9 belongs to the types (stage 2), risk 12 to future work ("Guard: none in this delivery"), and risk 14, the one stage 3 leaves unaddressed, is outside the range. Name them: 4 to 8, 10, 11, 13 and 14.
8. **Terms: "stage 1-4 | the four groups of commits in this document"** (L2599). The series has three commits before stage 1 (Decision, L482–483) and the supporting work, which Table 3 assigns to "2, 3, 4" or to no stage. Say "the four stages of What changes; the three commits before stage 1 and the supporting work are outside them".
9. **One table row names the jdss1 file and gives jdss2's size.** The "Compiled OpenAPI 3.1" row (L245) locates `b_jdss1_v4/out/openapi/openapi.yaml` and says "24,788 lines for jdss2 v4". The jdss1 file has 24,163 lines (counted today); the jdss2 one 24,788. Give the file's own size, or both.
10. **An absolute local path.** "local copy at `/home/user/repos/jdss-rest-api-spec`" (L1874) is a detail of one machine, which the README keeps out of records (L173–175), and the record already reaches the repository by relative link (L250: `../../../jdss-rest-api-spec/…`). "a checkout beside the plugin repository (`../jdss-rest-api-spec`); not on kub-gate" says the same without the home directory.
11. **Three dates for the writing.** Metadata: "written down 2026-11-09, merged into one record 2026-11-10" (L83); Advice: "The first version of this document (2026-11-05)" (L1648). A reader cannot tell which is the birth of the text. Say in Metadata: first written as a design on 2026-11-05, in this form on 2026-11-09, merged on 2026-11-10.
12. **"on jdss1 v3 they return an empty page"** (L1740, the paging gap's result) does not say which page was asked for. The hurl notes record that pages start at 0 and that a page past the end is 200 with an empty list; the record says the jdss2 test asked for `page=1` and `page=99` (L2157). If jdss1 v3 answered `page=1` on a short list, an empty page is the normal result and shows nothing about `page` without `per_page`. State the page asked for and what came back, so the sentence does not read as a difference in behaviour.
13. **Step 9 has a doubled conjunction**: "[…volume_key] and [bug_plugin_rest_volume_snapshots_stub] and [bug_plugin_rest_snapshot_exists_unrecognised]" (L1422), a leftover of the range replacement. One "and".
14. **A `crash` entry outside Crashes.** `crash_plugin_rest_endpoint_string_empty_addrs` has its heading under REST client behaviour (L2442); the README's kinds table says a `crash` lives under "Appendix, Crashes" (L103), and the Crashes intro has to point across (L2385–2387). Moving the heading keeps every link, since the anchor is the name; or the README says "usually".
15. **README: the area list lacks `rest`.** The seven compliance rules are `rule_rest_*`, an area that is neither `jdss_rest` nor `plugin_rest`, and the README's list (L118–121) does not have it; `kub-testing/issues/README.md` has the same list. Add `rest` (the API as the contract between plugin and appliance, where a rule binds both sides).
16. **README skeleton**: the Table of Contents in the skeleton (L225–227) shows `Option_A1…_adopted` and `Option_A2…` but not the one-option subsection the skeleton's body has (L303–304). Editorial.
