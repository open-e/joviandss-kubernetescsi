## Verdict

Steps 4, 5 and 6 are tests in the sense of the rule: a named build, a named baseline or a stated absence of one, prerequisites, a command, pass conditions a reader can observe. Step 1 is half a test and half an inventory of unit tests that the rule now excludes; step 3 is a cross-reference list, not a test; step 7 names an idea without the mechanism to carry it out; step 8 is a procedure. Three edges the record knows are checked by no step (the TLS handshake, the certificate error, the `{}` body on jdss1 v4), two pass conditions silently depend on implementation details that no item states, and no step says who runs it. Nothing here needs new evidence; most of it is rewriting, and three points need the user.

## Step by step

1. **Build and unit tests (kub-gate).** Keep: `go vet` on the current code first, with the result recorded, because no vet baseline exists; `go build` and `go vet` on every commit of the series, because `git bisect` needs every commit to build, a condition only the designer knows matters; `make test` on the last commit. Drop: the inventory of what the unit tests would cover (decoding, errors, fake server, crash fixes, security, with their sub-bullets). Each of those is the implementing agent's, and the edges in them already live where they belong: the required-field test in `impl_plugin_rest_fixtures_and_unit_tests`, the crash-fix tests in `impl_plugin_rest_crash_fixes`, the secret-free log and the escaped path in their items, the server that ignores `page` in the `per_page` commit's stop rule. Keep, reworded, the paragraph on what has no automated cover: the driver and controller changes, which kub-testing's T11 holds as seven checks (T11.1 to T11.7, each with the code it exercises and what it needs), exercised live by steps 4 and 5 only as far as csi-sanity reaches them. Say who runs the step: the user, or an agent on kub-gate; the analysis machine has no Go.
2. **Audit and compliance (analysis machine).** A test, but not yet constructible: the audit tool does not exist, so the step should say what the tool takes (`empirical/jdss1/v4/INDEX.md`, the `-src` schemas, `pkg/rest`'s list of calls) and what "passing" is (every call with every rule green, the exit code), or point at the item for the inputs and state only the expected output. One edge is missing and critical: the analysis machine has no Go, so `make check-types` must regenerate and diff without Go (Python and `diff`), or the step cannot run where the step says it runs. Who runs it: the agent on the analysis machine, after the user has refreshed the spec repository with `build_typespec.py --check`.
3. **NFS code.** Not a test: it lists NFS findings and says they have unit tests and are run live by step 5. Fold it: the findings into step 5's pass conditions, where most of them already are, and the sentence on `bug_plugin_driver_cleanup_type_check_before_error`'s NFS part into step 1's T11 reference. The number stays, with one line saying the step was folded into 5, so that "step 5" keeps its meaning everywhere.
4. **iSCSI cycle.** The best step: a command, a baseline, two prerequisites, four pass conditions. What another agent still lacks:
   - how the comparison is made: `dev_cycle.py` writes `summary.txt` with the changes against the previous usable cycle, and its `run_cycle` takes a `compare_to`; the step should say "compared with cycle `20261102-140341` through `compare_to`, read in `summary.txt`";
   - an observable for "reach the plugin's real logic": for example, the request log shows `GET pools/<pool>/volumes` answered 200 and the spec's result is not `Internal` with a decode message;
   - a dependency no item states: "the request log shows `per_page` on every list call" is readable only if the log line of each request keeps the path with its query string at Debug after `impl_plugin_rest_no_request_logging`; that sentence belongs in the item;
   - a pass condition that would miss the new failure: "no `plugin.log` contains `cannot unmarshal`" is Go's text for a type error; after stage 2 a missing required field fails with the field's name from `checkRequired()`, and `impl_plugin_rest_return_parse_errors` returns conversion errors with their own text. Name the error code or all the texts, and say the texts are part of the items;
   - how `cafile` or `insecure` reaches the lab: the config Secret `jdss-controller-cfg`, which `dev_cycle.py` deploys; and that the lab certificate is self-signed (risk 11), which is why one of them is needed at all;
   - an edge for `impl_plugin_driver_validate_names_and_ids`: csi-sanity makes its own volume IDs, and the current parser (`lunid.go:113-137`) already answers `InvalidArgument` to an ID without `_` or with an unknown prefix, so the baseline cycle shows which specs see that status today; the item changes the accepted set (characters, 131 characters). The step should state the statuses that must not move: `InvalidArgument` for a malformed ID, `NotFound` for a well-formed ID of a missing volume, which csi-sanity checks.
5. **NFS cycle.** Prerequisites and their owners are stated, the absence of a baseline is stated, the pass conditions are observable. Missing: who runs it (the user on kub-gate; the swap of builds is by hand until MF7 is solved), how the iSCSI build is restored afterwards, and where "every other failure is recorded as a new finding" goes (kub-testing `ISSUES.md`, an F row, and a name in `issues/test-findings.md`).
6. **Connected clients.** Constructible: a PVC and a pod, `iscsiadm -m session` on the node, the state on the appliance after deletion. Missing: how the appliance state is checked without the GUI (`GET pools/<pool>/san/iscsi/targets/<name>` answering 404, and the LUN gone from the target before that), which log is "the request log" (the controller's `plugin.log` at Debug), and where the replies kept "as the first v4 evidence with a client connected" go, since the spec repository is read only for this work and the hurl suite is the user's to extend: the cycle folder in `kub-testing/tmp/cycles/`, or a note for the user to add a hurl test.
7. **Connected clients, recommendation.** Not constructible as written: it says to send ControllerUnpublish and then DeleteVolume while the initiator is still logged in, but not how. Kubernetes does not delete a bound PVC while a pod uses it, so the calls have to be made directly, with a CSI command-line client against the controller socket, or by freeing the volume from the pod first and keeping the iSCSI session open by hand on the node. Say which, or say that the tester chooses and records the mechanism with the result. Say also that the step has no pass condition: it is exploratory, and its result is evidence for risk 8 either way.
8. **If a cycle failed.** A procedure, not a test; fine as the rule for failures, better placed in the section's intro with the other rules (the order, the latest release).
9. **Limits, after 0003.** An edge the implementer must know: five findings have no live cover until 0003 stops the controller crashes. Keep; "unit tests would be their only cover" becomes "no live cover in this delivery".
10. **Not testable here.** Keep. (The suggestion to add older JovianDSS 1 releases here lapsed the same day: the user decided question 29, older releases do not serve the same v4 and are not supported, so there is nothing to test.)

## Edges the record knows and no step checks

- **The TLS handshake** (risk 10's guard): `openssl s_client -tls1_3` against the lab appliance before the series starts, and against jdss1 only when no hurl run is active. It is a test, written in Risks and absent from Testing; it should be the first step, because its result can change stage 4.
- **The certificate error** (risk 11's guard): one connection to the lab appliance without `cafile` or `insecure`, checking that the error names the certificate problem and both settings. Only the real self-signed certificate shows it; a fake server would not.
- **The `{}` body on jdss1 v4** (question 30, risk 15): the question says "the live test answers it", and no step reads the answer. One pass condition in step 4 does it: every GET and every DELETE in the request log answered as the matrix records, none with 400 or 415.
- **The reply size limit** against the lab: the largest recorded reply is about 66 KB and the default 16 MiB, so the cycle proves nothing about `maxreplysize`; say so under step 10, or set it low for one focus run and check that the error names the limit.

## Who runs what

No step names its runner. The agent on the analysis machine cannot reach the cluster, `dev_cycle.py` runs on kub-gate, and the spec repository's tools are the user's. So: step 2 is the analysis-machine agent's; steps 1 and 4 to 8 are the user's or a kub-gate agent's; the results come back as the cycle folder under `kub-testing/tmp/cycles/`. The README now asks for this per step.
