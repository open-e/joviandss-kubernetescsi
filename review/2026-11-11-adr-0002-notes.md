## The two numbering regimes

- Identity numbers: risks, questions, testing steps, key observations,
  stages. Never renumbered; a retired entry keeps its number
  with a one-line pointer (step 3 → step 5); a list with gaps is written as
  bullets with the number in bold, because a Markdown renderer takes an
  ordered list's numbers from its first item and renumbers the rest (the
  user saw "question 24" on screen for question 29, then 30, in the source).
- Position numbers: tables, in order of appearance, renumbered when one is
  inserted or removed, with every "Table n" reference updated in the same
  change. The README assigns tables to both regimes (backlog 48). Priorities
  joined this regime on 2026-11-12, when the user added security as
  priority 2: a priority's number is its rank, so keeping the old numbers
  would have kept the wrong meaning; the six entries below it moved down
  and the 15 references in the record were rewritten in the same change.
  The dated reviews keep the old numbers.

## Lessons from the reviews

- A consistency review compares documents with each other, so an error
  propagated to every document passes it: the Decision sat inside Options
  considered in the record, the README row and the skeleton, and the review
  called the asymmetry "justified". Check the text against the requests of
  the day as well, and treat one's own same-day edits as claims to verify,
  not as the baseline. When a review flags a point and then finds a reason to
  keep it, say both.
- A decision's reach is the set of sentences that hedged because of it. After
  question 29 was decided, the hedge "or with a different v4" survived in
  Option A's price while the Problem statement, Context, Risks, Consequences
  and Advice had been updated. Search for the hedge wording, not the question
  number.
- A fix can narrow a rule too far: "snapshot `name` required in list entries
  only" was wrong because the NAS snapshot reply by name carries `name` and
  the NFS driver reads it. Check every reader of a field before stating where
  it is read.
- Review requests mean no edits; fixes wait for the user's word; the user
  commits. Reports go in `review/YYYY-MM-DD-<kind>-review.md`, with an
  Outcome paragraph added when fixes are applied.
- A quote the user gives to convey what a section is for is not a template.
  On 2026-11-11 the four problem-statement questions of ceejbot's post were
  copied into the README as a form (a bold sentence per part, "stated once",
  exclusions with a pointer each); the user corrected it on 2026-11-12: a
  Problem statement is a few coherent sentences that say the problem,
  answering one or all of the questions, never the tests or the unrelated
  issues. Write the understanding in the README's words, with an example and
  counter-examples, then check the record against it (backlog 54). The
  first replacement draft listed the instances (the failing calls, the
  client's faults, the fix's mechanisms) and was rejected as oversaturated:
  a Problem statement names the class of the problem; the instances are
  Context's.
